## 1. 目的

小〜中規模の劇団・自主公演で制作担当者が行う、企画・会場・予算・広報・チケット・当日運営・精算までの業務を、**公演プロジェクト単位で一元管理するブラウザ型制作支援OS**として構築する。
狙いは「タスクを登録すること」ではなく、各工程に必要な入力・計算・整理・出力をその場で行える**作業補助モジュール群**を提供すること。

### 基本思想

- 12工程は直列ではなく、時期によって複数が並行進行する。
- 各工程は独立した小ツール／モジュールとして作れる。
- 全モジュールは「公演マスター」と共通データ形式を参照する。
- カレンダーが「いつ動くか」を横断管理する。
- ダッシュボードは「今どのモジュールを開くべきか」を示す。
- 劇団ごとの差異を前提に、工程名・期限・使用モジュールを固定しすぎない。
- 最初から外部APIやクラウドDBを必須にせず、HTML/CSS/JavaScriptで成立するMVPを優先する。

## 4. 公演マスター

すべてのモジュールが参照する共通データ。

### 基本情報

- 公演ID
- 公演タイトル
- 劇団名
- 作品名
- 公演開始日／終了日
- ステージ一覧
- 劇場名・住所・担当者・連絡先
- 稽古開始日・稽古場
- 主催／共催／協力／後援
- 問い合わせ先
- 公式URL／SNS

### 人員

- 出演者
- 演出・脚本
- 舞台監督・照明・音響・美術・衣裳
- 制作
- 当日スタッフ
- その他スタッフ

### チケット基本情報

- 席種
- 座席数
- 前売／当日
- 一般／学生等の料金区分
- 販売開始日／終了日

### 共通利用の考え方

日時・料金・キャストなどを各モジュールで再入力させない。公演マスターを更新した場合、関連モジュールに「影響あり」を表示できる構造を目指す。
例：開演時刻変更 → チラシ／SNS／チケット／受付掲示物に変更注意。

## 5. 基本12工程とモジュール案

| 工程 | モジュールの役割 | 主な作業補助 |
| --- | --- | --- |
| 1. 劇場・日時 | 会場・日程設計 | 候補日、仮押さえ、本予約、利用料、支払期限、搬入搬出時間、劇場連絡先 |
| 2. 作品 | 作品情報管理 | 作品名、上演時間、脚本、上演許諾／権利確認、必要スタッフ |
| 3. 予算・料金・席数 | 収支シミュレーター | 固定費／変動費、席数、料金区分、想定動員、損益分岐点、売上目標 |
| 4. チラシ | 掲載情報整理 | 掲載必須情報、原稿、キャスト／スタッフ情報、校正状態、入稿／納品日 |
| 5. チラシ配布 | 配布先・部数管理 | 配布先、担当者、連絡状態、発送／手渡し、配布部数、残部 |
| 6. SNS・公演告知 | 広報進行 | 投稿カレンダー、投稿原稿、素材、媒体、投稿日、公開状況 |
| 7. チケット | 販売進捗 | ステージ別販売数、残席、売上、予約状況、販売経路 |
| 8. パンフレット | 掲載情報・原稿回収 | 構成、寄稿、プロフィール、広告、原稿締切、校正、入稿 |
| 9. 建込・仕込み | 劇場入り調整 | 搬入、仕込み、場当たり、ゲネ、撤収、部署別タイムライン、人員配置 |
| 10. 受付準備 | フロント準備 | 受付配置、掲示物、予約者資料、当日券、釣銭、備品、場内案内 |
| 11. 受付・物販・当日 | 当日運営 | 受付、もぎり、客席案内、物販、売上記録、トラブルメモ、アナウンス |
| 12. 決算 | 公演クローズ | 実績売上、経費、未払い、出演料／スタッフ費、収支差額、記録 |

## 6. リサーチから追加したい機能

### A. 稽古・連絡調整モジュール

制作の実務では、稽古期間のスケジュール管理や出演者・スタッフ間の調整が大きい。

- 稽古日／稽古場
- 参加者
- 欠席／遅刻
- 必要スタッフ
- 稽古内容メモ
- 次回までの連絡事項
- 全体連絡用テキスト生成
- スケジュール変更履歴

**優先度：高。** 既存12工程に明示されていないが、独立モジュール化する価値が高い。

### B. 契約・支払い管理

- 出演者／スタッフごとの契約状態
- 金額
- 請求書受領
- 支払予定日／支払済み
- 源泉徴収等の備考

**優先度：中。** 初期MVPでは予算・決算の簡易項目でよい。

### C. 助成金・協賛・広告

- 助成金候補・申請締切・採択額・報告書締切
- 協賛企業・広告枠・入稿状況・協賛金入金

**優先度：中〜低。** 劇団差が大きいためオプション向き。

### D. 交通・宿泊・ケータリング

- 対象者・移動手段・宿泊先・日程・金額・食事

**優先度：低〜中。** 地方公演や客演が多い団体向け。

### E. 申請・劇場提出物

- 劇場提出書類
- 消防等の申請
- 舞台図面
- 進行表・タイムテーブル
- 提出期限／提出済み／差戻し

**優先度：高。** 締切漏れ防止のためカレンダーとの相性が良い。

### F. 公演アーカイブ

- 完成チラシ・パンフPDF・舞台写真・記録映像
- 最終収支・来場者数・SNS実績
- 反省点・次回への引継ぎ

**優先度：中。** 継続利用するほど価値が増す。

## 7. カレンダー

OSの中核機能。各モジュールの予定・締切を一つの時間軸に集約し、「公演制作全体が今どこにあるか」を表示する。

### 表示

- 月間
- 今週
- 今日
- 本番まであとN日
- モジュール別フィルタ

### カレンダーイベント

各予定は必ず紐づくモジュールIDを持ち、クリックすると該当モジュール／該当作業へ移動する。
例：チラシ入稿 → チラシモジュール、SNS投稿 → SNSモジュール、劇場提出物締切 → 申請モジュール、仕込み → 建込モジュール。

### 本番日からの逆算テンプレート

- 本番90〜120日前：会場／作品／予算
- 90〜60日前：スタッフ・出演者確定、チラシ情報
- 60〜45日前：チラシ入稿・広報開始
- 60〜30日前：チケット発売
- 45〜14日前：配布／SNS／販売促進
- 30〜14日前：パンフ制作
- 14〜7日前：劇場提出物／受付準備
- 7〜0日前：最終連絡／仕込み／本番
- 本番後1〜14日：支払い／決算／記録

日数は劇団ごとに編集可能にする。

## 13. モジュールの独立性

各モジュールは単体でも起動・利用できるようにする。

- 公演予算シミュレーター
- チラシ掲載情報整理
- チラシ配布管理
- SNS投稿計画
- チケット販売進捗
- イベント・タイムスケジュール

OS化時は同じデータアダプタを介して公演マスターへ接続する。
> **開発思想**：OSを先に巨大実装してモジュールを埋めるのではなく、単体で価値のあるモジュールを作り、共通データ仕様を守りながら増やし、最後にカレンダーとダッシュボードで束ねる。

## 15. MVP境界

### MVPに必要

- 公演を1件作成／編集できる
- 公演マスター
- モジュール一覧
- 各モジュールの状態管理
- カレンダー
- 本番日からの逆算予定生成
- 今日／今週の予定
- モジュールへの導線
- JSON保存／復元
- まず3〜5個の実用モジュールを接続

### MVPでは不要

- ログイン
- 複数人リアルタイム共同編集
- Google認証
- 決済
- メール／SNSへの自動投稿
- 複雑な権限
- 会計ソフト連携
- チケット販売サイトそのもの
- 全12工程の完全実装

## 18. 現時点の結論

この企画は「劇団向けToDoアプリ」ではなく、**制作担当者が公演準備の各段階で実際に手を動かすための小さな業務ツール群を、公演データと時間軸で束ねた制作OS**として設計する。
プロダクトとしての核は以下の3点。

1. **公演マスター**：同じ情報を何度も入力しない
2. **制作カレンダー**：いつ何を始めるべきか分かる
3. **作業モジュール**：その場で実務を進められる

ダッシュボードはその3つを横断し、「今やるべき仕事」を提示する役割に限定する。
